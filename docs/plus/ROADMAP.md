# Форк CrossPoint для X4 Pro: заметки и упрощённый главный экран

Рабочий roadmap. Это не спецификация: он фиксирует установленные факты, принципы и открытые вопросы, которые надо закрыть до и во время реализации. Каждое решение записываем в раздел «Журнал решений» с причиной.

Дата сбора фактов: 28.10.2026. Апстрим: `crosspoint-reader/crosspoint-reader`, коммит `8f4d035` (ветка по умолчанию).

## 1. Установленные факты

### Устройство
- На устройстве: CrossPoint `1.6.5`, `device: xteink_x4_pro` (по `GET /api/status`), свободно ~121 КБ внутренней кучи после 4 минут работы.
- X4 Pro — ESP32-S3, 16 МБ flash, 8 МБ PSRAM, дисплей SSD1677 (800×480, 1 бит на пиксель в кадровом буфере), ёмкостный тач GT911, сенсорная кнопка Home, подсветка с регулировкой тепла, Wi-Fi и Bluetooth (`platformio.ini`, env `x4pro`; `USER_GUIDE.md`).
- Разделы flash: два OTA-слота по 6,4 МБ (`partitions.csv`). Текущая прошивка x4pro весит 5,63 МБ, запас ~0,9 МБ. Второй слот даёт откат при неудачном обновлении.
- На SD-карте уже лежит `crosspoint-1.6.5-x4pro-markdown-notes.bin` (5,77 МБ, на 134 КБ больше стандартной). Происхождение неизвестно — см. вопрос В0.4.

### Апстрим
- `SCOPE.md` прямо исключает заметки: «No notepads», «No typed notes, journals, or editors». PR с заметками не примут, поэтому форк — единственный путь, а не одна из опций.
- Там же есть оговорка про «downstream foundation»: продукто-нейтральные низкоуровневые примитивы для форков могут принять. Это шанс сократить наш дифф (например, настраиваемый набор пунктов главного экрана).
- Темп разработки высокий: 50+ коммитов за последний месяц, интеграция идёт в `develop`, железо вынесено в сабмодуль FreeInk SDK. Главный риск сопровождения — конфликты при ребейзе.
- Лицензия MIT: форк, переименование и распространение бинарников разрешены с сохранением копирайта.
- В репозитории есть `CLAUDE.md`/`AGENTS.md` и `.agents/rules/*` с жёсткими правилами по памяти, жизненному циклу Activity, i18n и проверкам. Их стоит соблюдать и в форке: так код останется совместимым с апстримом и понятным его авторам.

## 2. Принципы работы

1. **Минимальный дифф с апстримом.** Новое — в новых файлах (`src/activities/notes/`, `lib/Notes/`). Правки в существующих файлах — точечные и помеченные. Каждая фича за флагом сборки (например, `-DCPX_NOTES=1`).
2. **Стек патчей поверх релизных тегов апстрима**, а не поверх `develop`: релиз форка = тег апстрима + наши коммиты. Обновление — ребейз на новый тег.
3. **Файлы — источник истины.** Заметка — обычный файл на SD, который читается и правится с компьютера без прошивки. Индексы и кэши можно перестроить в любой момент.
4. **Сначала измеряем, потом оптимизируем.** Базовые метрики стоковой прошивки снимаем до первой правки, иначе «быстро» не с чем сравнить.
5. **Бюджеты как контракт.** Каждая фаза укладывается в бюджеты раздела 4 или явно их пересматривает.
6. **Внутренняя RAM дефицитна, PSRAM — нет.** На S3 крупные буферы держим в PSRAM (`HalMemory::allocatePsram()`), внутреннюю кучу — для DMA, стеков и драйверов.
7. **Железо тестирует человек.** Каждое изменение заканчивается чек-листом проверки на устройстве.
8. **Отдаём в апстрим нейтральные примитивы**, если они уменьшают наш дифф. Фичу «Заметки» не предлагаем: она вне его scope.

### Д4. Ввод текста и задержка отклика (главный риск проекта)
Решено (Р3): только тач-клавиатура. Первая попытка провалилась именно на скорости ввода, поэтому этот домен идёт первым и начинается с технического спайка.

**Что найдено в коде:**
- `KeyboardEntryActivity::render()` на каждое нажатие делает `clearScreen()`, перерисовывает заголовок, весь текст и всю клавиатуру и отправляет на панель весь кадр (`src/activities/util/KeyboardEntryActivity.cpp:740`). Для пароля Wi-Fi это терпимо, для заметок — нет.
- `HalDisplay` знает три режима: полный, `HALF_REFRESH` (~1,7 с) и `FAST_REFRESH` (своя LUT). Есть асинхронный вывод: вызов возвращается за ~25 мс, а панель обновляется сама 0,3–2 с (`FreeInkDisplay.h`).
- В драйвере SSD1677 есть экспериментальное оконное обновление `displayWindow(x, y, w, h)` с выравниванием по 8 пикселям (`Ssd1677Driver.cpp:760`), но обёртка в `GfxRenderer` закомментирована (`GfxRenderer.h:264`). Это главный кандидат на ускорение.

**Гипотезы ускорения** (проверяем замерами, а не верой):
1. Клавиатура рисуется один раз и больше не перерисовывается; отклик на нажатие — максимум инверсия одной клавиши.
2. После нажатия обновляется только окно текущей строки (или абзаца) через `displayWindow`, а не весь экран.
3. Конвейер «ввод → буфер → отрисовка» не блокирует опрос тача: нажатия, пришедшие во время обновления панели, копятся и выводятся одним следующим обновлением.
4. Раскладка текста инкрементальная: перевычисляется только изменённый абзац.
5. Ничего не пишется на SD на каждое нажатие (автосохранение с debounce).
6. Полное обновление против ghosting — только по паузе ввода или при выходе.

Узнать, насколько стабилен экспериментальный `displayWindow`, и как часто нужна полная перерисовка. По итогам — утвердить бюджет задержки (раздел 4).

## 4. Бюджеты (черновик, утверждаем в Фазе 1 после замеров)

| Метрика | Черновой бюджет |
|---|---|
| Рост бинарника | ≤ 150 КБ без BLE-клавиатуры |
| Внутренняя куча в простое | не хуже стока |
| Внутренняя куча в редакторе | −10 КБ максимум, крупное — в PSRAM |
| Тап «Заметки» → список на экране | ≤ 300 мс при 200 заметках |
| Нажатие клавиши → символ на экране | ≤ 150 мс (уточнить по возможностям частичного обновления SSD1677) |
| Холодный старт | не хуже стока |
